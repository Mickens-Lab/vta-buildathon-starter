# How to check what you run

Part of the [docs index](README.md). Where the images come from: [IMAGES.md](IMAGES.md). The pins: [PINS.md](PINS.md).

You should not have to take our word for what is inside the images this kit runs. Everything here is meant to let you check, with
free tools, that an image is the one the pins name, that it was built by this repository's published workflow, and what went into it.
Or to skip all trust and build it yourself and compare.

> **Status, stated plainly.** The signing steps are **written but have never run on GitHub**. Until the images workflow has run
> for real, there is no signature or attestation to check, `pins.json` records no digests, and `npm run images:verify` will say
> `INCOMPLETE` (published image) rather than `VERIFIED`. What is tested without GitHub: the verification logic against mocked
> `gh`/`cosign`/`docker` output, the workflow's structure and permissions, and the label format. What is **not** yet observed: that
> the attest and sign jobs succeed, that the real `gh attestation verify` / `cosign verify` output matches what the command
> expects (the identity pattern and the SPDX predicate type are taken from the tools' documentation), that anyone can verify
> anonymously once the packages are public. Treat each as **unverified** until the first real run has been checked with the
> commands below. The stopgap images that were pushed by hand were not built by the workflow and **will fail** the check
> (`label origin`), by design.

## The 60-second version

```sh
npm run images:pull                 # fetch the pinned images (by digest once pins.json records it)
npm run images:verify               # checks all three; PASS / FAIL / SKIPPED per check, then a verdict
npm run images:verify -- vta        # one image
npm run images:verify -- --local    # an image you built yourself with images:build: labels only
npm run images:compare              # line your local build up against the published one
npm run pins:check                  # also warns while an image is pinned by tag instead of by digest
```

Install **one** of these to check signatures (without either, the signature checks are `SKIPPED` and the verdict is `INCOMPLETE`,
exit code 2; it never passes silently):

- **GitHub CLI** (`gh`, 2.49 or newer, for `gh attestation`): <https://cli.github.com>, then `gh auth login` once. It also reads the SBOM.
- **cosign**: <https://docs.sigstore.dev/cosign/system_config/installation/> (for example `brew install cosign`, or the release binary).

Verdicts: `VERIFIED` (the digest is the pinned one and a signature from this repository's workflow checked out), `FAILED` (something
did not match: do not run that image), `INCOMPLETE` (nothing failed but a needed check could not run), `LABELS-ONLY` (a local build).

## The trust model, in plain language

**What we sign.** The images workflow ([`.github/workflows/images.yml`](../.github/workflows/images.yml)) builds each image from the
exact upstream commit in `pins.json`, pushes it, and then, for each image:

1. a **build provenance attestation** (SLSA style): a statement signed by GitHub, naming this repository, the workflow file, the
   commit and the run that produced the image digest;
2. an **SBOM attestation** (SPDX, generated by `syft` from the pushed image): the list of packages found inside, per platform;
3. a **cosign signature** of the multi-arch index digest, made keylessly with the workflow's GitHub OIDC identity (Sigstore records
   it in a public transparency log; no private key exists to leak or lose).

Everything is signed **by digest**, never by tag, because a digest names exact bytes and a tag can be moved.

**What a good check proves.** That the bytes with this digest were produced by a run of *this repository's* images workflow (on `main`
or an `images-*` tag), and that the labels (upstream commit, features, Dockerfile hash) were written by that run. Together with the
digest in `pins.json` (which is committed and reviewed in git), it also proves you got the image the maintainers pinned and not a
substituted one, even if the registry or the network were tampered with.

**What it does not prove.**

- That the *software* is safe or bug-free. A signature says who built it and from what, not that it is good.
- That the **upstream source is trustworthy.** The VTA and VTC come from the [VTI repository](https://github.com/OpenVTC/verifiable-trust-infrastructure)
  and the mediator from [affinidi-messaging-mediator](https://github.com/affinidi/affinidi-messaging-mediator), at the commit pinned in
  `pins.json`. The workflow checks it fetched exactly that commit; it does not review the code, and Cargo pulls dependencies from
  crates.io (`--locked`, so the versions in the upstream `Cargo.lock`, but not audited here). That is the trust boundary: we trust the
  pinned upstream commits as much as you do. The pins say which commit; reading them is up to you (below).
- That the **base images and OS packages** are unchanged in the world. The Dockerfiles start from `rust:<version>-bookworm` and
  `debian:bookworm-slim` by tag and run `apt-get install` without version pins, so a rebuild next month can differ. The SBOM lists
  what was in *this* build.
- That the **signing identity is only this repository.** Anyone who can run the workflow on `main` (maintainers with write access) or push
  an `images-*` tag can publish a signed image. Branch and tag protection on the repository decide who that is. There is no
  `pull_request` trigger on purpose.
- That the image is **fit for anything but development.** These are **DEV ONLY** images. The mediator is built and run with an
  **open ACL** (any DID may register and relay), the VTA keeps a plaintext seed on its volume, and tunnel mode exposes public URLs.
  A valid signature on a deliberately insecure dev setup is still an insecure dev setup: see [SECURITY.md](SECURITY.md) and
  [MODES.md](MODES.md).

## Check a pulled image

The easy way is `npm run images:verify`. It does the following, and you can do each step by hand.

```sh
# 1. The digest you have is the digest pins.json records (the digest is the identity; the tag is a hint)
jq -r '.images.vta.digest' pins.json
docker image inspect ghcr.io/mickens-lab/vta-buildathon:fc157f76 --format '{{json .RepoDigests}}'

# 2. The GitHub attestation: signed by this repository's images workflow
DIGEST=$(jq -r '.images.vta.digest' pins.json)          # "null" until the digests are recorded
gh attestation verify "oci://ghcr.io/mickens-lab/vta-buildathon@$DIGEST" \
  --repo Mickens-Lab/vta-buildathon-starter \
  --signer-workflow Mickens-Lab/vta-buildathon-starter/.github/workflows/images.yml

# 3. The cosign signature, with the exact identity and issuer (the workflow on main, or an images-* tag)
cosign verify "ghcr.io/mickens-lab/vta-buildathon@$DIGEST" \
  --certificate-identity-regexp '^https://github\.com/Mickens-Lab/vta-buildathon-starter/\.github/workflows/images\.yml@refs/(heads/main|tags/images-.+)$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

# 4. The labels: what the image says it was built from
docker image inspect ghcr.io/mickens-lab/vta-buildathon:fc157f76 --format '{{json .Config.Labels}}' | jq
jq '.vti.vta | {ref, features}' pins.json      # org.buildathon.vti-ref and org.buildathon.vta-features must equal these

# 5. The SBOM of your platform's image (the per-platform digest is inside the index)
docker buildx imagetools inspect "ghcr.io/mickens-lab/vta-buildathon@$DIGEST"      # lists one digest per platform
gh attestation verify "oci://ghcr.io/mickens-lab/vta-buildathon@<platform digest>" \
  --repo Mickens-Lab/vta-buildathon-starter --predicate-type https://spdx.dev/Document/v2.3 --format json \
  | jq '.[0].verificationResult.statement.predicate | {spdxVersion, packages: (.packages | length)}'
```

Use the other image names for the VTC (`vtc-buildathon`) and mediator (`mediator-buildathon`). Images published by a fork: set
`IMAGE_REGISTRY=ghcr.io/<their-org>` and `VERIFY_REPO=<their-org>/<their-repo>` for `images:verify`, or edit the commands above.
The expected signer lives in `pins.json` (`images.verify`).

A failed check prints why. `no attestations found` or an identity mismatch is a **FAIL**: do not run the image. Being offline, not logged in
to `gh`, or too old a `gh` is a **SKIPPED** with the reason, not a pass and not a failure.

## Check an image you built yourself

```sh
npm run images:build vtc
npm run images:verify -- --local vtc       # labels against pins.json
npm run images:compare vtc                 # against the published image of the same pin, if you have pulled it
```

`images:build` records the same labels the workflow does: `org.buildathon.vti-ref` (or `mediator-ref`), `pinned-ref`, `upstream-source`,
`vta-features` (VTA), and `dockerfile-sha256`, plus `build-origin=local`. What `--local` can and cannot show:

| | |
|---|---|
| Can show | The labels say your image was built from the pinned commit, with the pinned features (including `tsp`), from a Dockerfile with this hash. |
| Cannot prove | That the contents match the labels. Labels are written by whoever builds. A local build has no signature and no SBOM (run `syft <image>` yourself for one). `VTI_LOCAL=1` builds your working tree and is labelled `local`, not the pin. |

For the real assurance when you build yourself, the source is yours: you ran `git archive` on the pinned commit from your own checkout of the
upstream repository (`images:build` exports exactly that ref, not your working tree), you can read the Dockerfile you built with, and you
did not have to trust a registry at all.

### Reproducibility: what is and is not claimed

**Bit-for-bit reproducibility is not claimed**, and not tested. Two builds of the same pin are expected to produce the **same labels but
different image IDs**, because:

- the base images are referenced by tag (`rust:1.95-bookworm`, `debian:bookworm-slim`), not by digest, so they move over time;
- `apt-get install` is not version-pinned, so package versions follow Debian's current archive;
- layer timestamps and the image's `created` time differ between builds.

`--locked` Cargo builds do fix the Rust dependency versions, and the upstream commit is exact, so the *source* is reproducible even where the
*bytes* are not. `npm run images:compare` reports which provenance labels agree, whether the image IDs are identical (they will normally not
be), and how many layers match from the bottom. A difference in the ID is therefore expected; a difference in `pinned-ref`, `vti-ref` or
`dockerfile-sha256` is a real finding. Making the build reproducible would mean pinning the base images by digest and the apt packages by
version (a snapshot mirror); that is not done.

(An existing local `vtc-buildathon:local` and its `:93d36996` tag having the same ID only means one was tagged from the other.)

## Audit what goes in

- **The pins.** `pins.json` is the single source of the upstream commits. Check them against upstream yourself:
  `git ls-remote https://github.com/OpenVTC/verifiable-trust-infrastructure vta-service-v0.65.0` should print the `vti.vta.ref` commit
  (tags can be moved; the commit is what is built). `npm run pins:check` does this for the release tags if you have a checkout, and
  [PINS_LOG.md](../PINS_LOG.md) says why each pin is what it is.
- **The Dockerfiles.** The VTC and mediator Dockerfiles are in this repository: [`docker/vtc.Dockerfile`](../docker/vtc.Dockerfile) and
  [`docker/mediator.Dockerfile`](../docker/mediator.Dockerfile). The VTA is built from the *upstream* `Dockerfile` at the pinned commit
  (`git -C ../verifiable-trust-infrastructure show <ref>:Dockerfile`). Each image carries the sha256 of the file it was built with
  (`org.buildathon.dockerfile-sha256`); compare: `sha256sum docker/vtc.Dockerfile`. A different hash with a matching `revision` label
  means the image was not built from this file.
- **The entrypoints and build arguments.** [`vta-entrypoint.sh`](../vta-entrypoint.sh), [`vtc-entrypoint.sh`](../vtc-entrypoint.sh) and
  [`mediator-entrypoint.sh`](../mediator-entrypoint.sh) run inside the containers: read them, they are short. The features each image is built
  with are in `pins.json` and in its labels.
- **The workflow.** Read [`.github/workflows/images.yml`](../.github/workflows/images.yml): every action is pinned to a full commit SHA, the job that
  runs the upstream build has no signing permission (only `attest` and `sign` have `id-token: write`), and secrets are limited to the
  built-in `GITHUB_TOKEN`. `scripts/test/images-workflow.test.ts` enforces these.
- **The dependencies.** Read the SBOM (step 5 above) or run your own `syft`/`grype` over the image. The SBOM is a list, not an audit.

## If something does not check out

Do not run the image. Re-pull it by digest (`npm run images:pull -- --force --by-digest`), re-run `npm run images:verify`, and compare with a
local build (`images:build`, `images:compare`). If it still fails, or you think a published image or a pin is wrong, open an issue on this
repository with the output of `npm run images:verify` and the digest you have; do not post secrets or logs containing keys. For a suspected
compromise (a signed image that should not exist), say so in the title and give the digest and the workflow run URL from the attestation, without
publishing an exploit; the maintainers can then revoke the package version and re-pin. A problem in the VTA, VTC or mediator source itself
belongs to the upstream project.
